# 研究助手检索流程重构方案（workflow-first，react-as-backstop）

调研日期：2026-10-19。借鉴来源（均为实际通读源码，不是 README）：
[PaperSeek](https://github.com/paperseek/paperseek)（源码缓存在 `.audit-acceptance/paperseek_src/`，18 个核心文件）、
[aghababaeiali/research-agent](https://github.com/aghababaeiali/research-agent)（`agent/graph.py` + `agent/nodes/`）、
[Jack1447/PaperAgent](https://github.com/Jack1447/PaperAgent)（`src/graph/workflow.py` + `src/agents/`）、
[NirDiamant/GenAI_Agents scientific_paper_agent](https://github.com/NirDiamant/GenAI_Agents)（24.6k★）。

## 一、目标架构

三个开源项目在检索核心上殊途同归：**LangGraph 负责编排，LLM 只在定点做决策，API 工具干活，没有一家用自由 ReAct 跑检索主链**。据此把我们的模式从"react 为主、workflow 为辅"翻转为：

```
用户消息 → router（现有，改判定规则）
  ├─ direct：闲聊/概念直答（不变）
  ├─ plan：意图明确的请求，含复合指令「找→析→存」（扩展为默认主力）
  │   流水线：拆查询 → 双源检索 → 本地重排 → LLM 打分 → 精读留证
  │         → 覆盖评估（循环补检，research-agent 式回边）→ 综合分析
  │         → [可选] 逐篇分析 → [可选] 存工作区 → claims/judge 质检 → finalize
  └─ react：模糊单轮、上下文追问、混合突发意图（保留降级为兜底 + 历史节流）
```

复用映射总表：

| 我们的环节 | 借鉴来源 | 来源文件 |
|---|---|---|
| 查询计划 SearchPlan | PaperSeek | `query_planning.py`（prompts.py 的 `SYSTEM_SEARCH_INTENT_ANALYSIS`） |
| 查询方言编译 | PaperSeek | `query_compiler.py` |
| 查询调整闭环 | research-agent | `graph.py: should_continue_searching`（6 行判断函数） |
| 标题漂移检测（纯代码质量信号） | PaperSeek | `query_planning.py: _title_drift` |
| 候选重排漏斗 | PaperSeek | `retrieval_fusion.py`（RRF 加权）+ `ranking.py`（LLM 绝对量表） |
| 反思两级判定（规则先行 LLM 殿后） | PaperAgent | `src/agents/reflection.py` |
| 并行逐篇分析（map-reduce） | PaperAgent | `workflow.py: dispatch_summaries` + `Send()` |
| 分档预算 + token 计量 | PaperSeek | `budgets.py`、`decision_client.py` |

## 二、具体改造项（按实施顺序）

### P0 — 成本可观测（一切的前提，抄 PaperSeek `decision_client.py`/`budgets.py`）

1. **token 计量落库**：在 `backend/app/infrastructure/llm.py` 的 complete 返回中记录 `usage.input_tokens/output_tokens`，在 `AgentState` 加 `tokens_used`，随事件推到 SSE（`_compact_update`）。现有预算只有调用计数（`state.py: MAX_LLM=24` 等），没有 token 维度。
2. **分档预算预设**：新增 `backend/app/agents/budgets.py`，仿 PaperSeek `SEARCH_BUDGET_PRESETS` 定义 fast/medium/high 三档（max_iterations、候选池、打分上限、深读次数），在创建任务时按用户/前端选择载入，替换现在的散列常量。

### P1 — workflow 升级为主力（核心）

3. **SearchPlan 替换 `decompose`**（改 `backend/app/services/analysis/attribution.py:337`）：
   - 输出从"2–4 条查询字符串"改为强类型计划：`question_type`（8 类枚举）、`core_concepts`、`must_have_facets`、`optional_facets`、`likely_synonyms`、`boundaries`、`query_views`（2–3 个互补视角，组内 OR 组间 AND）。照搬 PaperSeek `SYSTEM_SEARCH_INTENT_ANALYSIS` 的防过约束规则（不把 optional 塞进 AND、successor 视角不与原标题术语 AND）。
   - 两级修复：JSON 解析失败重试一次 → 结构有缺口时把原输出塞回 messages 补全 → 最终兜底退回现在的简单改写。全部走现有 `cached_call("plan", ...)` 缓存。
4. **查询方言编译器**（改 `backend/app/services/search.py:225` 新增 `compile_query_view()`）：
   - arXiv：concept_groups 编译为 `all:"a" AND (all:"b" OR all:"c")`，替换现在的"空格拆词全 AND"；S2 同步支持 OR 组。
   - 编译是纯函数，不让 LLM 写数据库语法（PaperSeek 两级设计）。
   - 启用现在产而未用的 `exclusions` 字段：S2 侧作 `NOT` 词，arXiv 侧过滤。
5. **候选本地重排**（改 `search.py: merge_papers()` 之后新增 `pre_rank_candidates()`）：
   - 确定性加权分：BM25（标题+摘要，复用现有 FTS）+ embedding 余弦（复用现有向量设施）+ 查询词覆盖率 + 源端 rank 先验，权重照抄 PaperSeek `retrieval_fusion.py` 的显式配比思路。
   - **替换 `tooling.py:413` 的"丢弃最旧"为"按预排序分保留 top-K"**——这是现有最不合理的一处截断。
6. **LLM 相关性打分**（新增节点，接入 workflow `search_node` 之后）：
   - 候选超阈值（如 >20 篇）时触发；绝对量表 0–10、rubric 挂 must_have_facets、**禁止用引用数当相关证据**、temperature=0、分数与理由分两次调用。
   - 照搬 PaperSeek 批处理：切块重试、部分失败降级保留本地序。打分结果写入 state 供 assess 节点消费。
7. **覆盖评估闭环加固**（改 `backend/app/agents/tooling.py` 的 `route`/`_rule_assess`）：
   - 抄 research-agent 的 6 行判断函数风格，把 `route()` 改写成显式的"质量达标 / 迭代上限"双终止（现在是链式 if，读不出结构）。
   - **标题漂移检测**（抄 PaperSeek `_title_drift`，纯代码）：意图信号词在 top-5 标题覆盖率 <20% → 即使数量够也判 insufficient，这是给 LLM 不可用时的规则回退一个真正的"质量差"信号，解决 `new_query` 恒为 None 的断腿。
   - **规则路径确定性改写**：命中漂移/结果为空时，纯代码策略改查询（optional_facet 降级、拆最重的 AND 组为两条子查询）。
   - **查询指纹反重复**（抄 `query_history.py: query_fingerprint`）：assess 循环内重复查询即停。

### P2 — workflow 尾部扩展（"找→析→存"一站式）

8. **router 判定规则调整**（改 `prompts.py` 的 `ROUTER_SYSTEM` + `agent.py` 的 `plan_route`）：
   - 明确规则：用户一句话包含检索+分析/保存等复合指令 → plan；模糊单轮、追问、混合意图 → react；简单问题 → direct。
   - `TaskRoute` 输出加 `post_actions: ["analyze", "save_to_workspace"]` 字段，驱动尾部节点开关。
9. **尾部节点**（`workflow.py` 新增，复用现有工具函数 `_call()`）：
   - `analyze_papers_node`：对入选论文逐篇跑现有 `analyze_paper` 流程；多篇时用 **LangGraph `Send()` 并行分发**（抄 PaperAgent `dispatch_summaries`），配 dict reducer 合并结果。
   - `save_to_workspace_node`：调现有 `add_papers_to_workspace` 工具逻辑写工作区（写操作仍走现有 HITL `_confirm` 确认，不绕过）。
   - 图边：`synthesize_evidence → [post_actions 含 analyze] analyze_papers → [含 save] save_to_workspace → claims`。
10. **评估走两级判定**（抄 PaperAgent `reflection.py`，改 `workflow.py: assess_node` / `run_coverage_assessment`）：
    - 规则先行：论文数 < 阈值、标题漂移 → 直接判失败，不调 LLM；
    - LLM 殿后：`_is_pass` 只认显式 "PASS"（防客套误判），非 PASS 原文作为 feedback 注入下一轮（对应 NirDiamant 的 `JudgeOutput.feedback` 回灌）。

### P3 — react 降级 + 瘦身（兜底路径）

11. **历史节流**：工具返回（尤其 `search_papers` 候选列表）以精简形式（ID+标题+年份，top-10）注入 messages，详情按需重拉；或对大工具结果做一轮压缩摘要。目标：兜底盘的 token 降到现在的 1/3 以下。
12. **react 提示词收敛**：`_react_system` 加"能进 plan 的复合指令不要在这里硬扛"的边界说明；保留现有 react ⇄ workflow 的回边（judge 补证回 react 是 ReAct 的合理使用场景，不变）。

### 明确不做（避免过度设计）

- 不引入 PaperSeek 的引用网络扩展车道（citation lane）——我们的 `get_paper_references/citations` 工具已覆盖，重排阶段不急需。
- 不引入 RAGAS 在线评估（research-agent 的 evaluator 节点，其作者自己标注生产可关）——我们的 claims/judge 已承担质检，重复。
- 不引入 PaperAgent 的独立 reading/review/compare/recommend 边——那是另一个交互形态，与现有工具重叠。

## 三、验证方式

- 每步跑 `backend/tests` 现有 agent 测试套件；改 `merge_papers`/截断逻辑时补候选排序的单测。
- 固定一组 10 个中文调研问题（含 3 个复合指令问题、3 个追问）做改动前后对比：候选 top-5 命中率、assess 轮数、judge 通过率、`tokens_used`（P0 落地后可直接读数）。
- 验收标准：复合指令问题 100% 走 plan 不走 react；同题 token 消耗较现状降 ≥40%；LLM 不可用场景下检索不再断腿（规则改写路径生效）。

## 四、风险与回滚

- SearchPlan 改造初期 decompose 失败率可能上升——两级修复 + 兜底退回旧路径保证可用；`AGENT_PROMPT_VERSION` 必须 bump 使旧缓存失效。
- LLM 打分节点增加一次调用——本地重排先行，打分只对超阈值批次触发，且受 P0 分档预算约束。
- workflow 尾部写工作区是新增副作用——复用现有 `_once` 操作账本和 `_confirm` 确认，不重写副作用控制。
- 全部改造在既有 LangGraph 图内加节点/改边，react 与 direct 路径不动，可分批合入、逐批回滚。
