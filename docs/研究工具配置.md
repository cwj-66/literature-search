# 研究工具配置

聊天工具目录由 `backend/app/tools/research.py` 统一维护，函数参数由 Pydantic 模型生成 JSON Schema。`app.tools.TOOLS` / `CHAT_TOOLS` 只包含下列 14 个工具，`FUNCTION_TOOLS` 可用于兼容的 Function Calling 接口。当前 Agent 继续沿用原有 JSON ReAct 调用协议，统一 ToolNode 已注册这些工具。

| 业务模块 | 聊天工具 |
| --- | --- |
| 论文发现 | `search_papers`、`get_paper_details`、`find_related_papers`、`get_paper_references`、`get_paper_citations` |
| 工作区 | `list_workspace_papers`、`add_papers_to_workspace`、`remove_paper_from_workspace` |
| 分析与证据 | `analyze_paper`、`get_paper_analysis`、`retrieve_paper_evidence`、`read_paper_context` |
| 图谱与样本统计 | `query_knowledge_graph`、`analyze_research_trends` |

`acquire_paper_fulltext`、`parse_paper`、`index_paper` 放在 `BACKGROUND_TOOLS`，不提供给聊天模型。旧检查点使用的覆盖度评估、收藏和深读工具名保留执行兼容，但不出现在模型的新目录中；不新增回答问题或比较论文的工具。

## 工作区和范围

Router 现在区分 `direct`（普通聊天/通用概念）、`react`（简单研究任务）和 `plan`（复杂研究任务）。普通聊天经过直接回答节点返回，不调用工具，也不进入论文主张提取和 Judge；论文相关任务保持原研究流程。工作区聊天页的两种模式都先经过 Router，标准模式跳过检索计划确认，Deep Research 保留计划确认。显式通过 API 指定 `mode=react/plan` 时仍保留强制研究模式。

研究任务 `POST /api/research/tasks`、SSE 新建任务和检查点都保留以下上下文：

```json
{
  "workspace_id": "真实的工作区 ID",
  "scope": "selected",
  "current_paper_id": null,
  "selected_paper_ids": ["论文 ID"]
}
```

- `current` 必须指定当前论文。
- `selected` 仅在已选论文中操作；没有已选论文时可以搜索、查看发现的论文元数据，无法隐式检索全库。直接工具调用可以用 `paper_ids` 明确指定范围。
- `workspace` 必须显式选择，查询工作区成员集合；空工作区返回空数据。
- 所有本地分析、原文检索、上下文、图谱和统计都会检查成员关系。论文别名和本地 ID 统一解析，不能通过换 ID 越过范围。
- 聊天中的新增、移除和深度分析走现有 HITL 中断，恢复只执行批准的论文 ID。检索式确认由任务的 `auto_approve` 单独控制。

工作区聊天页已经使用 Agent，而非按关键词直接选择搜索或分析。范围在页面明确选择；默认不扫描整个工作区。旧浏览器工作区会在发起任务前注册到后端并补充原有论文成员，任务完成后同步成员变化，保留本地阅读状态和笔记。

## 调用接口

`GET /api/tools` 返回 14 个聊天工具及 3 个后台能力的目录。

统一入口：`POST /api/research/tools/{tool_name}`。

```json
{
  "arguments": {"query": "retrieval mechanism", "limit": 8},
  "context": {
    "workspace_id": "demo",
    "scope": "selected",
    "selected_paper_ids": ["已入库论文 ID"]
  }
}
```

上例用于 `retrieve_paper_evidence`。`POST /api/tools/{tool_name}` 也支持新增工具；原先已有的搜索、分析、加入工作区、解析、索引接口保留原请求格式。为了所有工具使用相同协议，优先使用 `/api/research/tools/`。

后台能力无法通过统一聊天工具入口调用。HTTP 400 表示参数语义或范围不合法；422 表示参数结构不合法；404 表示未知工具或工作区；502 表示外部服务错误；503 表示本地存储不可用。引用源不可用时，工具返回 `status: unavailable` 和原因，不将其解释成没有引用。

## 后台导入流程

新增工作区成员后，为新论文写入 SQLite 持久队列：公开 PDF 获取 → MinerU 结构化解析 → 保存正文/结构 → 硅基流动 Embedding → SQLite 文本块 + FAISS 向量。聊天工具立即返回排队状态，不等待解析。重复加入不会重复排队；一个论文在多个工作区共用处理结果。解析成功而索引失败时保留原文，后续处理可复用。

队列由应用启动时的 worker 消费。`PAPER_PROCESSING_WORKER=0` 可暂停消费；默认 `1`。正常关闭会重新排队在途任务；进程异常退出后，超过 30 分钟的处理租约可重新领取。失败/全文不可用状态保留，不自动反复调用收费服务；维护时可检查 `paper_processing` 状态和服务配置。

上传 PDF 入口同样保留 MinerU 的结构化文本和页码，并以同一正文建立索引。旧数据缺少页码时返回 `null`。读取上下文和检索只读取已有索引，不触发重新下载、解析或索引。

`retrieve_paper_evidence` 对范围内 FAISS 向量进行相似度计算，和关键词结果做 RRF 融合；返回 `chunk_id`、论文 ID、原文、章节、起止页码、语义分数和关键词命中数。嵌入服务不可用时明确提示并降级到关键词；没有已保存文本块时返回 `not_indexed`。`read_paper_context` 返回同一篇论文中命中文本块左右最多 3 块。

## 服务配置和结果边界

需要在项目 `.env` 配置 MinerU、硅基流动和现有语言模型服务密钥，配置示例见 `.env.example`。Semantic Scholar Key 为可选，但限流会影响引用查询、推荐与搜索。

- `MINERU_API_TOKEN` / `MINERU_API_BASE` / `MINERU_MODEL` / `MINERU_POLL_LIMIT` / `MINERU_POLL_INTERVAL`
- `SILICONFLOW_API_KEY` / `SILICONFLOW_BASE_URL` / `SILICONFLOW_EMBEDDING_MODEL`
- `SEMANTIC_SCHOLAR_API_KEY` 与既有语言模型配置

论文发现复用既有搜索/推荐服务；推荐需已入库种子。引用查询目前最多返回来源前 20 条，`complete=false`，不宣称完整引文网络。趋势工具始终标注当前样本；少于 20 篇或不足 3 个年份时只做描述统计。主题来自已保存的分析关键词，缺失年份和分析的数量均返回。

Agent 将原文证据、元数据记录和样本统计分别标注。元数据和统计可支撑其本身的事实，不用于证明论文的科学结论或夸大领域趋势。
